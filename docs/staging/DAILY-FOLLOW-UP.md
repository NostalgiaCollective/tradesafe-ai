# Daily follow-up usability

The rendered prior Actions page hid current progress, offered only Assigned to me / Include closed filters over the first 200 loaded rows, and lost the selected action when returning from a report. The dashboard combined work and verification requests into one open count. This focused milestone improves that existing system without changing database fields, statuses, roles or command semantics.

- Dashboard: a direct outstanding-actions entry and separate exact counts for Needs attention and Awaiting verification. Workers see their assignments; supervisors/owners see company totals, under existing membership/RLS rules.
- Actions: server-filtered Outstanding, Needs attention (open/in progress), Awaiting verification, Completed (closed) and All actions; Assigned to me or Company actions; bounded 25-row pages. Counts cover the authorized set, not just the loaded page.
- Each row brings the original finding, latest saved progress and permitted next step together. Assignment/due date/controls, amendment evidence and audit history remain expandable. Request verification, Verify and close, and Reopen action make the existing transitions explicit.
- Validated return destinations retain scope, status, page and selected action. Returning opens and focuses that row. If a saved action moved outside the filter, it remains selected with an explicit notice; list counts still follow the filter. Native filter navigation retains supported unsaved-leaving warnings. It does not persist unsaved input after navigation/reload.
- The existing revision, actor binding, request-ID retry and immutable-original protections are reused. Forms retain input during failed/ambiguous requests. No new fields, migrations, statuses, notifications or offline promises.

`tests/fixtures/follow-up.mjs` exercises real worker/owner/supervisor workflows against persisted records, two isolated synthetic companies, 28 actions plus a separate-company finding, real private photo/PDF bytes and separate correction evidence. It covers counts, server pagination, empty state, keyboard/focus, filter return, save/reload, failures before commit and after commit, double taps, one history event on retry, denied worker closure/assignment, stale revisions, supervisor close/reopen, unchanged originals/hashes and revoked-access denial.

The shared scenario runs in Linux WebKit against disposable local Supabase and in Chromium against local or hosted staging (`node --use-system-ca scripts/staging/follow-up.mjs [--hosted]`). Hosted execution requires the exact passed commit in `EXPECTED_COMMIT`; credentials stay in ignored files. Request aborts are simulated faults, while persistence and authorization results cross real application/server boundaries. Synthetic fixtures and receipts are retained. Failure receipts suppress raw fields, credentials and requests.

The required WebKit job now executes four source scenarios. The previously completed synthetic recovery regression stays unchanged and required; it is not a new hosted recovery claim. No external email, domain configuration, billing or production changes.

The durable checkpoint and `.staging/daily-follow-up-delivery.md` record final commit, exact CI, staging identity, executed results and screenshots. The new physical-phone follow-up sequence remains pending until Daniel reports it: outstanding actions → Needs attention → Update progress → Save progress → reload → Open original observation → Back to actions → Request verification. A supervisor can then use Awaiting verification → Review and verify → Verify and close.
