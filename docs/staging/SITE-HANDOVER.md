# Site handover and daily summary

The existing site workspace now has **Daily handover**, a date/timezone selector, **Refresh summary** and **Download handover**. It reuses briefing versions, acknowledgements, submitted concerns, Actions and immutable action events. Workers see only the rows allowed by existing RLS; it introduces no permissions or underlying workflow changes.

The selected day means server-recorded briefing activity, concern submission and action verification in the chosen timezone (America/Toronto by default, America/Winnipeg or UTC explicitly selectable). Entered work dates are displayed separately. Start is inclusive and next midnight exclusive, including daylight-saving transitions. Acknowledgements are counted for each exact version as of refresh, not as a reconstruction of what was known that day. Attendance is separate; missing acknowledgement does not establish absence.

Outstanding work includes all currently unresolved actions, even from earlier days. Verification events remain in the selected-day section after reopening; current status is labelled separately. Responsibility, reassignment needs, progress and original-record links reuse existing data. Member labels are current; captured briefing names retain their recorded attribution. A closed action never certifies a safe site.

The additive migration `20260929000100_site_handover.sql` introduces one STABLE SECURITY INVOKER read function. Its statement snapshot supplies every section and permission check together. No existing record, RLS policy, applied migration, retained export or content-review state is changed. A query failure produces no summary; more than 200 records per section, 2,000 acknowledgements or 2 MiB fails explicitly without a partial handover. The caller must retain current site access. The API is enabled only in the existing staging recording environment.

The authorized downloadable HTML reuses the daily-brief export approach (escaped content, private/no-store response, restricted content security policy). Each download generates a fresh complete snapshot with its own timestamp, date boundaries, site revision and authenticated original-record links. It is not a retained immutable trade PDF, contains no photo binaries and sends no notifications. Existing exports remain unchanged. For larger sites, use original lists and arrange a complete export; no unbounded automatic export is introduced.

Navigation stores only selected date/timezone, expansion positions and scroll position in session storage, scoped by actor/site. No report content, credentials or offline data is stored. A reload re-fetches authoritative data. Failed reads retain the selected day, explain the failure and offer **Retry handover**; duplicate in-flight reads/downloads are prevented.

Verification covers SQL midnight edges, 23/25-hour days, caller RLS and whole-response limits; browser tests cover authoritative counts, version acknowledgements, responsibility, verification/reopening, original records, mobile keyboard/navigation, failed-read retry and downloaded snapshot content. Exact local WebKit, hosted Chromium, CI and deployment receipts are in the durable checkpoint and `.staging/site-handover-delivery.md`. Screenshots are inspection evidence, not executed workflow tests. Physical handover acceptance is pending until reported separately.
